# Containerizing the runtime: proof of concept and plan

> This proof-of-concept has been productized -- see [`../docker/README.md`](../docker/README.md)
> for the maintained version. Kept here as the original dated record.
>
> Companion to [`ALPACA-REVIEW.md`](ALPACA-REVIEW.md) (enhancement E7) and [`AGENTS.md`](../AGENTS.md).
> Everything below was actually run (not just designed) in throw-away Docker containers on this machine;
> nothing in the repo was touched, and all test containers/networks were removed afterward. The commands
> are included so you (or an agent) can rerun this verification later.

## The one design choice that matters: don't rewrite the roles

There are two ways to make Alpaca's output run in a container:

1. **Translate each Ansible role into a Dockerfile** that does the same thing a different way. Faster per-build,
   but now there are two implementations of "what makes the PHP app vulnerable," and they will drift.
2. **Point the existing, unmodified `ansible/roles/*` at a running container instead of a VM**, using Ansible's
   own container connection plugin in place of SSH.

(2) is the only one that doesn't touch the content you want preserved, so that's what this proves out: the exact
same `apache` and `vsftpd` roles from this repo, byte-for-byte, configuring a container.

## What was actually tested

```
docker pull geerlingguy/docker-ubuntu2204-ansible   # a systemd-capable Ubuntu image, built for exactly this purpose
docker run -d --tmpfs /tmp --tmpfs /run --tmpfs /run/lock \
    -v /sys/fs/cgroup:/sys/fs/cgroup:rw --cgroupns=host \
    geerlingguy/docker-ubuntu2204-ansible /lib/systemd/systemd     # target, systemd as PID 1

# control side: ansible-core (already in review/repro's image) + two packages + one collection
apt-get install -y docker-cli python3-docker
ansible-galaxy collection install community.docker   # already bundled with the `ansible` apt package

# inventory: one line
alpaca-target ansible_connection=community.docker.docker ansible_python_interpreter=/usr/bin/python3
```

Then `ansible-playbook` ran a real playbook using the **real, unmodified `apache` and `vsftpd` roles** from
`ansible/roles/`, with no edits to either role. Result: all 10 tasks and 3 handlers succeeded, and I confirmed the
services were genuinely live, not just "changed: true": `curl` got HTTP 200 from Apache, and port 21 accepted a
real TCP connection for vsftpd — through `systemctl`-managed services inside the container, exactly as they'd run
in a VM.

**Two real gotchas, both one-time control-node setup, not role changes:**
- The `community.docker.docker` connection plugin needs the **Python** `docker` SDK (`python3-docker`), not
  necessarily the CLI — but current Ansible also shells out to the `docker` binary for some operations, and on
  this machine's Debian-based image that's a separate package (`docker-cli`) from the daemon package (`docker.io`).
  Both are one-time additions to the *control* image, nothing in the repo.
- **Ubuntu 18.04's stock Python (3.6) can no longer run modules generated by current Ansible** (`from __future__
  import annotations`, a Python 3.7+ construct) — I hit this first, before switching the target to 22.04. This
  isn't a container-specific problem: it would bite a real 18.04 VM over SSH exactly the same way with a modern
  Ansible control node, and it's already on the roadmap as U1/U5 in the main review (migrate off 18.04). The
  container path doesn't add a new dependency here; it just surfaces the existing one sooner.

## Timing (measured, not estimated)

| Step | Time |
|---|---|
| Full provision from scratch (destroy container → fresh systemd container → `ansible-playbook` runs both roles) | **2m 14s** |
| `docker commit` the provisioned container into a reusable image (one time, per lattice) | a few seconds |
| Reset from that baked image (destroy → fresh container → services already active and serving) | **1.1s** |

That gap is the whole design: **bake once per lattice, reset instantly per student.** Compare to the existing
Packer/VirtualBox path, which the paper puts at ~25 minutes per machine, from an ISO.

## Proposed architecture

```
 once per lattice (can run ahead of class, even overnight)         during class, per student, repeatable
+-----------------------------------------------------+     +---------------------------------------------+
| existing Prolog pipeline (unchanged)                 |     | docker compose -p student-017 up -d          |
|   createRangeFromIGS -> playbook.yml + roles         |     |   (seconds; fresh container from the image)  |
|                         |                             |     |                                               |
|                         v                             |     | "reset" = down -v && up -d                   |
| ansible-playbook (community.docker connection,       |---->|   (same ~1s; no re-provisioning)             |
|   the SAME roles/ as the VM path) -> provisioned     |     |                                               |
|   container -> docker commit -> per-lattice image    |     | each Compose project gets its own network,   |
+-----------------------------------------------------+     | so per-student IPs fall out for free         |
```

Because each separate `createRangeFromIGS` run already produces fresh random passwords (confirmed earlier: running
it twice gave `X*0zH` and `P18E&YLl`), **running the Prolog generator once per student, then baking each result,
already gives every student distinct credentials with zero changes to the generator.** A true reproducible-seed
feature (E3 in the main review) would only add the ability to *regenerate* a specific student's exact instance
later — it's a nice-to-have on top of this, not a prerequisite.

For a class of size N: bake N images (in parallel, ahead of time — N independent ~2-minute jobs, not N serial
25-minute VM builds), then each reset during the exam is the ~1 second path.

## What this phase does *not* include yet

- The fleet script (loop over a roster, call the Prolog generator N times, bake N images, write a manifest of
  student -> ports/IPs/image) — straightforward given the above, not yet built.
- The instructor dashboard, parameter editing, connection/command logging, and flag system from the management-
  interface list — separate pieces, intentionally not started until you say which is next.
- `mysql`/`php` roles weren't exercised here (they still hit the independent B2/B3/B6 bugs from the main review
  regardless of VM or container — that's not a container problem, it's the existing bug). Worth re-running this
  same proof against the full `web_admin_access` lattice once those are fixed, to confirm the mechanism holds for
  every role, not just the two tested here.
- VirtualBox/Packer stays exactly as-is — this is an *additional* path, not a replacement.

## Suggested next slice

A `review/repro`-style script that: takes an already-generated `ranges/<id>/<lattice>/` folder, runs the
provision-and-bake step against a fresh systemd container automatically, and leaves a tagged image behind —
basically turning the manual steps above into one command. That's the natural next concrete deliverable if you
want to keep going on this before moving to the fleet script or the dashboard.
